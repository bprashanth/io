# Execute v2: local-first NGO insight pipeline

## Mission

Build and benchmark an executable data-to-dashboard pipeline for a workshop of
about 20 nontechnical NGO participants. A participant supplies an unfamiliar
CSV, Excel workbook or PDF, or asks for public data, then uses short ordinary
Indian English to request a desktop dashboard and refine it through follow-up
questions.

The system must use a laptop-sized model for as many analysis/query requests as
possible, escalate detected failures to `qwen/qwen3.8-27b`, and use a frontier
model only through a hard privacy boundary that exposes the participant's
question plus a value-free schema/structure/standard/outline. A frontier model
must never receive real rows, distinct values, min/max values, real aggregates
or hydrated screenshots. Real data may be used by the small local model and the
27B tier. During hosted screening, only public or synthetic fixtures may be
sent to OpenRouter; the deployment claim requires local replay.

Find a pipeline we can credibly demonstrate at the event. Do not rathole into
installers, model tuning or an open-ended coding-agent contest. Do not tailor
production prompts, code, connectors or routing to fixture sectors, named
places, expected answers or benchmark wording.

## Product architecture under test

```text
file or downloaded official source
  -> structure-preserving local ingest
  -> conversation + typed dataset contract
  -> laptop model proposes a declarative analysis plan
  -> grammar/schema/binding/invariant checks
       -> detected failure: Qwen 3.8 27B re-plans with data
       -> detected failure: frontier re-plans from value-free schema only
  -> trusted local DuckDB execution
  -> typed result bundle with provenance
  -> validated visual/layout specification
  -> deterministic self-contained renderer and filtered export
  -> browser acceptance checks
  -> finished desktop dashboard and persistent follow-up state
```

SQL is an execution backend, not the whole model contract. The plan must also
represent region selection, durable filters, grouping, derived measures,
denominators, joins, comparisons, rankings, missing-data treatment, provenance,
causal limits, chart intent, clarification and escalation. Extend the existing
analysis-plan schema only for general operations proven necessary by more than
one data shape.

Grammar-constrained decoding (GBNF, Outlines or an equivalent supported method)
guarantees parseable syntax, not correct meaning. A perfectly valid query can
still select the wrong table, column, denominator, period or join. Measure exact
executed results and conversation obligations, not SQL-string similarity.

Do not use an 8B model to turn trusted JSON into HTML. Rendering is deterministic.
A frontier visual tier may return only a whitelisted declarative chart/layout
specification. It may not return executable JavaScript or hydrate real values.
Local code validates the spec and fills it with the trusted result bundle.

## Privacy boundary

Implement the frontier boundary as an allowlist serializer, not a warning in a
prompt. The outbound frontier request may contain:

- participant language after any explicitly configured redaction;
- table, sheet, page and region identifiers;
- column names where policy permits, declared types and units;
- structural relationships and the plan/visual JSON Schema;
- synthetic placeholder values with impossible canary markers.

It may not contain raw rows, sampled values, distinct labels, min/max values,
real summary statistics, calculated results, downloads or screenshots. Before
sending, compare the serialized payload against locally observed cell values
and fail closed on a match. Persist the exact value-free request for audit.

For this hosted benchmark, only public or synthetic data may be sent to the
small or 27B OpenRouter tiers. A claim that private data stays local requires an
identical replay with the small model and Qwen 3.8 27B served locally.

Event files do not automatically become training data. Retain raw participant
files or conversations only with explicit consent and a documented retention
policy. Default logs contain hashes, model/route metadata, validated plans,
errors and scores, not private rows.

## Model search policy

The first tier must fit a mid-grade Windows laptop. Screen credible 2B--9B
query/SQL/structured-output models, including the proposed XiYan 3B/7B,
Arctic-Text2SQL 7B and a current general 7B--9B control only after verifying
their exact repository, licence, context, architecture and DuckDB suitability.
Treat the existing Heartwood 2B/9B adapters as compatibility ablations, not
assumed winners.

Use OpenRouter first when the exact model is available and assert the resolved
model/provider. Download only candidates unavailable through OpenRouter or
finalists needing local replay. Prefer `hf download` with resume support; if it
fails, try `aria2c` against resolved files. Verify checksums/revisions. Do not
redownload existing weights. If workspace storage is insufficient, place model
caches under a task-specific directory such as `/mnt/seagate/io-models/` after
checking that exact mount and available capacity. Never move or alter unrelated
model caches or shared running services.

Qwen 3.8 27B is the second tier. Use OpenRouter for development and replay the
frozen finalist locally on the DGX before making a privacy or deployment claim.
The third tier is a frontier model behind the mandatory value-free serializer.

Stop a laptop candidate early after at least three representative tasks if it
has two silent critical errors, cannot emit/execute a valid plan in two tasks,
or is clearly below the 85% gate with no plausible recovery. Do not early-pass.

## Accuracy and routing gate

Keep 85% as the first practical milestone. Report it precisely:

- standalone first-rung execution accuracy after at most one constrained repair;
- accepted-plan accuracy;
- detected-failure recall and silent incorrect-acceptance count;
- routed final accuracy after 27B/frontier escalation;
- escalation rate by reason, latency and cost.

A laptop model qualifies for the first rung when it achieves at least 85% exact
result-and-obligation accuracy on the frozen development suite. The routed
system must still have no observed critical wrong-number, fabricated-source,
unsafe-claim or broken-application failure in the counted suite. Escalation may
improve final system accuracy but must not be credited to the small model's
standalone score.

Allowed route signals are observable without an oracle or fixture identity:

1. malformed or schema-invalid plan after one repair;
2. absent/incompatible column, region or operator;
3. read-only execution error, impossible denominator, or contradictory scope;
4. unresolved ambiguity returned as a typed clarification;
5. semantic critic rejection derived from the participant conversation and
   value-free structure, not candidate paraphrases;
6. browser error, missing required content, stale durable state, broken export
   or overflow.

No routing rule may mention a sector, case ID, fixture value, named place or
holdout label. Save every route decision.

## Cases and ground truth

Reuse existing cases for regression. Add only enough new cases to cover missing
general data shapes. Freeze development and untouched holdout membership before
model selection. Do not inspect holdout answers while modifying the pipeline.

Test data patterns rather than sectors:

- flat categorical/time/numeric tables;
- multiple sheets and repeated or adjacent subtables;
- merged/nested headings, formulas, blanks and notes;
- digital and scanned PDF tables;
- filtering, drill-down, ranking and time/group comparison;
- derived rates versus counts and percentage-point changes;
- missing/suppressed values and incompatible units or periods;
- multi-file joins and unresolved label matches;
- official-source discovery, citations and downloads;
- correlation without causal overclaim;
- optional spatial operations only when the input supports them.

Use at least five terse/paraphrased participant phrasings per isolated query
task and retain multi-turn context for follow-ups. Gold evidence consists of
the exact result set plus durable scope, required provenance, allowed equivalent
interpretations, caveats, download obligations and browser behavior. Gold SQL
may be retained for debugging but is not the sole oracle.

## Sequential execution plan

### S-1: preserve and preflight

- Inspect `git status`; preserve unrelated changes and untracked files.
- Record current commit, versions, disk capacity and available model caches.
- Verify credential files exist without reading them into logs.
- Create the pinned benchmark runtime.
- Reproduce one preserved split run and its oracle/browser check into a new run
  directory. Never overwrite historical evidence.

### S0: freeze v2 contracts and cases

- Extend the typed plan/result/visual contracts only where generic operations
  are missing.
- Freeze the v2 development and holdout manifests, exact messages, source hashes,
  oracles, scoring and route policy.
- Commit before running candidates.

### S1: isolated laptop-model gate

- Evaluate candidate models on conversation + structure -> typed plan/query.
- Compare exact executed result sets and obligations.
- Run grammar-constrained decoding as a named ablation where supported.
- Record standalone accuracy, one-repair accuracy, latency, memory/quantization,
  failures and estimated Windows fit.
- Advance every candidate meeting 85%; if none does, advance the best candidate
  only as a detected-failure router experiment and say the laptop gate failed.

### S2: routed complete pipelines

Evaluate at least:

- laptop winner -> deterministic execute/render;
- laptop winner -> Qwen 3.8 27B on declared failure -> deterministic render;
- laptop -> 27B -> value-free frontier plan/layout on declared failure;
- Qwen 3.8 27B direct -> deterministic execute/render as the open large-model
  control;
- Antigravity default and Cline/Qwen 3.8 27B from existing identical artifacts
  for calibration, with fresh product runs whenever cases or protocol differ.

Do not use old Antigravity scores for a changed dataset, message sequence,
timeout or rubric. Only actual Antigravity/Cline product runs support claims
about those products; custom split harnesses are architecture comparisons.

### S3: rendered journey verification

For every counted final page:

- open it in Playwright/Chromium;
- exercise each control and the filtered download;
- check values, units, durable scope, source/provenance and causal limitations;
- record console/page/network errors and desktop overflow;
- save and personally inspect every final screenshot at 1440x1000;
- grade chart suitability, hierarchy, labels, palette, density and finish using
  the existing 100-point rubric and 10-point visual scale.

Do not require three chart types per dashboard. Prefer one suitable chart over
decorative variety. Judge variety across cases where different visual families
are analytically justified. A blinded multimodal judge may assist but is never
the sole judge, and a Gemini-family model cannot be the only visual judge of
Antigravity.

Use the existing event budgets unless frozen before the batch: five minutes to
the first useful page, two minutes for a normal follow-up and ten minutes hard
stop per turn. At most two automatic repairs means at most three total attempts.

### S4: local replay and event decision

- Replay the winning laptop model locally with its exact revision,
  quantization, grammar/template and context.
- Replay Qwen 3.8 27B locally on the DGX if feasible in this run; otherwise make
  no local privacy or concurrency claim and leave exact replay commands.
- Report measured hosted provider errors separately from model capability.
- Do not infer 20-user capacity from single-user latency. Give only a clearly
  labelled projection until a separate load test exists.

## Final deliverable

Produce a clear pitchable decision:

1. smallest laptop model reaching or missing the 85% standalone gate;
2. exact local footprint and Windows feasibility;
3. frozen escalation policy and observed escalation rate;
4. final routed correctness, visual quality, latency and cost;
5. comparison with actual observed Antigravity, including its faults;
6. proof that frontier requests were value-free;
7. what is ready for the 20-person event and what still requires local replay,
   packaging or load testing.

The desired result is not a SQL leaderboard. It is the smallest dependable
system that lets a nontechnical participant go from unfamiliar data to a
correct, attractive, cited and revisable dashboard without debugging.
