## Goal

Build and validate a portable **“big local brain” event kit**:

> Plug a fast external SSD into an Apple Silicon Mac with roughly 32 GB unified memory, start DwarfStar/DS4, and expose DeepSeek V4 Flash as a local OpenAI-compatible model that can be used by an agent harness.

The intended role is **not** high-throughput chat. The model is a slow, high-capability planner/orchestrator: it receives a question, decides what information or computations are needed, calls tools/local worker nodes, inspects their returned results, and synthesizes the answer.

The model itself and all inference should be local. No API key or cloud model should be required.

You have >1 TB of SSD available at:

```bash
/mnt/seagate
```

Use that as the staging area. Do not download large model files into the system/root disk.

## 1. Stage DwarfStar and DeepSeek V4 Flash

Create:

```bash
mkdir -p /mnt/seagate/io-event-kit
cd /mnt/seagate/io-event-kit
```

Clone current upstream DS4:

```bash
gh repo clone antirez/ds4
cd ds4
```

Immediately record the exact code version:

```bash
git rev-parse HEAD | tee ../ds4_commit.txt
```

Download the preferred DeepSeek V4 Flash Q2 imatrix model:

```bash
./download_model.sh q2-imatrix
```

DS4's current downloader stores the GGUF under `./gguf/` and sets `./ds4flash.gguf` to the selected model. The Q2-imatrix build is the relevant low-memory/SSD-streaming target; the file is roughly 81 GiB.

Record exactly what was downloaded:

```bash
ls -lh gguf/
readlink ds4flash.gguf || true

sha256sum "$(readlink -f ds4flash.gguf)" \
  | tee ../model_sha256.txt
```

Also record available space:

```bash
df -h /mnt/seagate
```

Do **not** start with MTP/speculative decoding. First establish a stable SSD-streaming baseline. SSD streaming and MTP have had recent compatibility work/issues, so treat MTP as a later optimization rather than part of the event-kit MVP.

## 2. Build DS4 on the staging machine

First identify hardware:

```bash
uname -a
nvidia-smi || true
```

Use the appropriate upstream build:

```bash
# Apple Silicon Mac
make

# DGX Spark / GB10 Linux
make cuda-spark

# Other NVIDIA CUDA Linux
make cuda-generic
```

Then:

```bash
./ds4-server --help
./ds4 --help
```

Do not assume flags from old documentation if current `--help` disagrees. Record the output in:

```bash
../build_info.txt
```

The final event SSD should contain the **source and model**, not depend on a Linux-built binary. On the participant's Apple Silicon Mac we should compile DS4 locally with `make`; the ~81 GiB GGUF can remain on the external SSD.

## 3. Validate `ds4-server`

The end state we care about is:

```text
Agent harness
     │
     │ OpenAI-compatible API
     ▼
127.0.0.1:8000
     │
  ds4-server
     │
DeepSeek V4 Flash
     │
external SSD
```

`ds4-server` exposes OpenAI-style chat/completions and supports tool schemas/tool calls, which is what makes it usable underneath an agent harness rather than merely as a chat CLI.

On a low-memory Mac, start conservatively:

```bash
MODEL=/path/to/ds4flash.gguf

caffeinate -i ./ds4-server \
  -m "$MODEL" \
  --ssd-streaming \
  --ctx 8192 \
  --host 127.0.0.1 \
  --port 8000
```

For Linux/CUDA validation, use the corresponding CUDA invocation if required by the current build:

```bash
./ds4-server \
  --cuda \
  -m "$MODEL" \
  --ssd-streaming \
  --ctx 8192 \
  --host 127.0.0.1 \
  --port 8000
```

Check:

```bash
curl -s http://127.0.0.1:8000/v1/models
```

Then smoke-test inference:

```bash
curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "deepseek-v4-flash",
    "messages": [
      {
        "role": "user",
        "content": "Explain in three bullets why a planner might divide a large data-analysis job into smaller independent tasks."
      }
    ],
    "temperature": 0,
    "max_tokens": 300,
    "stream": false
  }'
```

Do not optimize anything until this works repeatedly.

## 4. Important: DS4 is the model server, not the agent

The event concept requires another thin layer above DS4.

Configure an OpenAI-compatible agent harness approximately as:

```text
BASE_URL=http://127.0.0.1:8000/v1
MODEL=deepseek-v4-flash
API_KEY=local-dummy-value
```

The harness should maintain the planning loop:

```text
question
   ↓
DeepSeek planner
   ↓
tool call
   ↓
tool result
   ↓
DeepSeek planner
   ↓
another tool call if necessary
   ↓
final answer
```

For the first prototype, do not give the model broad shell/filesystem access. Mock the eventual hive interface with three constrained tools:

```text
find_sources(query)

describe_source(node_id, source_id)

run_local_task(node_id, source_ids, instruction)
```

The tools can initially return canned JSON. The purpose is to prove that the locally streamed model can operate correctly **as an orchestrator**.

Later these tools will route over the LAN to private IO/9B worker nodes.

## 5. Benchmark the thing we actually care about

Produce one markdown/CSV benchmark report. Do not just report “the model runs.”

### A. Basic operational benchmark

Measure:

```text
hardware
RAM
OS
DS4 commit
model checksum
model size
SSD type/interface
sequential SSD read speed

server startup time
peak memory usage
crashes/OOMs

prefill rate
decode tokens/sec
time to first useful output
```

Run at least:

```text
ctx = 8k
ctx = 16k
ctx = 32k
```

Stop increasing context when memory pressure becomes unreasonable. For this use case, a reliable 8–16k planner is more valuable than forcing a huge context.

### B. Cold vs warm SSD run

Run the same deterministic prompt several times.

Record:

```text
first/cold run
second run
third run
```

We specifically want to understand how much expert caching changes practical latency.

If the current DS4 version exposes `--ssd-streaming-cache-experts`, benchmark automatic/default behavior first, then try a small controlled sweep such as:

```text
4 GB
8 GB
12 GB
```

only if those values are safe on the test machine.

Do not assume “larger cache = faster”; low-memory SSD-streaming tests have shown that extra cache can sometimes increase memory pressure and hurt performance.

### C. External-SSD benchmark

The final product depends on the model **remaining on the removable drive**.

Test:

```text
internal SSD → model
external SSD → model
```

with otherwise identical settings.

Measure:

```text
sequential read MB/s
startup
prefill
decode tok/s
```

This is important because current low-memory Mac reports mostly demonstrate SSD streaming generally; we should not assume a random external USB drive performs like Apple's internal NVMe.

The final kit should therefore target a **fast USB4/Thunderbolt NVMe SSD**, not a normal thumb drive.

### D. Planner benchmark

This matters more than a generic chatbot benchmark.

Give the model a fake room containing e.g.:

```text
Node A:
  attendance.xlsx
  budget.xlsx

Node B:
  annual_report.pdf
  whatsapp.txt

Node C:
  volunteer_log.xlsx
```

Ask:

> Which centres appear to need intervention, what might explain it, and produce the information needed for a dashboard.

The model should have only the three mock tools above.

Build the mock responses so that it must:

1. discover the relevant sources;
2. inspect their metadata;
3. request a numerical calculation from one node;
4. request text/PDF analysis from another;
5. notice an intermediate result and request one additional check;
6. synthesize the evidence.

Run ~10 planner tasks of this form.

Record:

```text
valid tool-call rate
correct tool chosen
correct node/source chosen
whether arguments are valid
number of unnecessary calls
whether it follows up after intermediate evidence
whether final answer agrees with returned evidence
total planner tokens
wall-clock time
```

This is the actual go/no-go test for the event idea.

A model at 2–3 tok/s may be perfectly usable if it spends 20–40 seconds producing a short plan and then delegates the expensive data work to parallel local workers.

### E. Long-output benchmark is secondary

Do one 500–1000-token generation to establish decode speed, but do not optimize the event kit around long-form generation.

Our intended use is closer to:

```text
slow big model:
"Call nodes 2, 5 and 7 with these tasks."

workers:
do the work in parallel

slow big model:
"Given these results, make one more check."

workers:
return evidence

slow big model:
synthesize
```

So **short reasoning/tool-call latency** matters more than “how quickly can it write a 3,000-word answer?”

## 6. Expected target

There are recent reports of DeepSeek V4 Flash using DS4 SSD streaming on a 36 GB M4 Max at about **3.2 tok/s on stock DS4**, with experimental optimizations reaching roughly **4.6 tok/s**. Treat those as useful comparison points, not promises for a 32 GB machine or an external SSD.

For our MVP, I would consider the experiment successful if a 32 GB Apple Silicon Mac can:

```text
start reliably from a model stored on the external SSD;
stay within available memory;
sustain roughly >= 1.5–2 tok/s;
make valid multi-step tool calls;
complete a useful planner cycle in < ~60 seconds;
run several cycles without instability.
```

Anything around 2.5–3+ tok/s from the external drive would make the proposition considerably more attractive.

The question is **not** “does this feel as snappy as ChatGPT?”

The question is:

> Can an ordinary 32 GB laptop carry an ~81 GiB local slow brain that is smart enough to plan work for faster local workers?

```text
│   ├── source...
│   └── gguf/
│       └── DeepSeek-V4-Flash-....gguf

├── scripts/

│   ├── smoke-test.sh
│   └── benchmark-planner.py
├── benchmark-results/
│   ├── staging-machine.md
│   └── target-mac-template.md

```

`setup-mac.sh` should install/check only what is genuinely required, compile DS4 locally, find the GGUF on the attached volume, and verify its checksum.

`run-server-mac.sh` should start DS4 in conservative SSD-streaming mode and clearly print:

```text
Local model ready:
http://127.0.0.1:8000/v1
model: deepseek-v4-flash
```

The portable drive should require **no model download at the event**.

Do not spend time polishing an installer yet. First prove:

```text
external SSD
   +
32 GB Mac
   +
DeepSeek V4 Flash Q2
   +
ds4-server
   +
multi-step tool-using harness
```

and return the benchmark results, exact commands, failures, and recommended configuration.
